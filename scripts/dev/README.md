Build and push images first, or import them into this single node's k3s
containerd. For local imports also register the repository@sha256 digest alias
with k3s ctr --namespace k8s.io images tag <imported-tag> <repository@sha256:digest>
so CRI can resolve it without an unpublished registry pull. Use an exact registry manifest digest. Frontends must be rebuilt
with dev API and WS URLs; reusing a staging frontend image targets staging.
The first installation's three frontend images were built from
`e0d875ba612517cd7aac3b184a2deff41cb0fec3` and imported locally, not pushed to GHCR.
They remain dependent on this node's image cache until published.

On a host with this repository and the intended kubeconfig:

```sh
python3 scripts/dev/update_images.py --image user=ghcr.io/poryadok/voiceroot/user@sha256:<64hex>
python3 scripts/dev/update_images.py --image user=ghcr.io/poryadok/voiceroot/user@sha256:<64hex> --apply
```

Repeat `--image` for multiple services. First command previews with server
dry-run; second updates only main app images and waits for rollout. Only the
owned `voice-dev` namespace is admitted. UID/resourceVersion CAS guards against
concurrent edits; an atomic ConfigMap lock serializes this tool. A failed or
uncertain mutation retains `voice-dev-image-update-lock`. Inspect the Deployment,
rollout and lock UID before manually resolving it; do not blindly delete it.
The updater never resets stores, applies migrations or changes configuration.

The separate `repair_clickhouse_memory.py` is a fixed DEV-only maintenance
operation for the recurring populated-store startup OOM: preview with no flags,
then `--apply` from reviewed Linux source under the current TT DEV claim and
fresh deploy admission. It changes only ClickHouse's 2Gi memory limit to 4Gi;
the 256Mi request, image, full remaining spec and PVC identity stay unchanged.
Check actual node memory headroom first. The tool checks namespace ownership,
the digest-pinned single-container StatefulSet, quota, server dry-run, full-spec
and UID/resourceVersion CAS, Bound PVC UID before/after, then rollout/readback.
It uses the same `voice-dev-image-update-lock` as the app image updater and
retains that lock on uncertain mutation/rollout. No force unlock, rollback,
table deletion, broad apply, pool tuning or Preservation service operation is
provided. Keep the TT resource window through independent verification;
neither the lock nor TT fences unrelated external kubectl operations.
The 4Gi rollout can still OOM while the ClickHouse server uses the image's
default `max_server_memory_usage_to_ram_ratio=0.9`. The separate
`mitigate_clickhouse_memory.py` is an opt-in DEV-only trial for that exact
partially completed operation. It requires the retained updater lock UID and
operation marker plus the StatefulSet, current 4Gi Pod, and Bound PVC UIDs.

UID/resourceVersion/full-spec-guarded StatefulSet patch. `--apply` creates only
`voice-clickhouse-memory-policy` with `clickhouse-memory-0.8.xml`, then mounts

existing `docker_related_config.xml`. The image digest, 4Gi container cap,

the original lock on any uncertain result and releases it only after a new
Ready Pod, unchanged PVC/image/spec, parsed ratio `0.8`, and a startup log
reporting the derived 3.20GiB server cap. The ratio is a reversible trial,
not proof that startup OOM will stop. Keep the TT DEV claim/window until
independent smoke and resource readback; do not rerun the initial repair,
force-delete a pod, or remove a retained lock on timeout.

## Fresh installation only

`environment.py` renders captured staging workload/configuration identities into
paused dev resources and rejects foreign namespaces, Secrets, host access and
unresolved Secret references. `credentials.py` uses the Linux NATS issuer under
its dedicated UID and generates independent keys; see its CLI help. Public CA
inputs and the JDK truststore must match the selected Auth image.

`bootstrap.py prepare --secrets <fresh-secret-list> --revision <40hex>` captures
source configuration/images and prepares root-only JSON under
`/home/voice-dev/bootstrap`. It reads staging configuration, never staging Secret
payloads. `start` exclusively creates `voice-dev`, provisions fresh directories,
starts stores, bootstraps central NATS streams before consumers, runs SQL
migrations, then apps and routes. It refuses nonempty data directories or an
existing namespace. This is host-specific operational tooling, not an unattended
installer for arbitrary clusters. Bootstrap configuration input must be reviewed
against the matching source revision; captured live images can be mixed revisions.

Recovery actions (`activate`, `central-bootstrap`, `repair-fresh-nats-claim`,
`rotate-postgres`, `configure-routes`) are operator tools scoped to the owned dev
namespace. `activate` can apply captured app configuration; do not use it for
routine updates. Never use bootstrap to reset an existing dev installation.
Captured state includes secrets and must remain root-only.

## DEV media JWKS issuer recovery

`media_pki.py` is a separate DEV-only issuer/rotation tool. It never accepts a
namespace argument and refuses to run outside the designated Linux operator
host. The issuer runs as UID/GID 10001 in a pinned local image
with a Docker named volume at `/state`; the image initializes that volume as
0700 and all generated CA/leaf key files are 0600. No CA key is put in a
Kubernetes Secret, host bind mount, container socket, command argument, terminal
output or receipt. `apply` streams the new material from the volume through
process memory directly to `kubectl` stdin; it does not write the key-bearing
payload to a host file. Receipts contain only public fingerprints, resource UID
and resourceVersion pins, the prior public trust bundle, and Role trust-path
settings. The pmd Docker operator is the custody administrator: Docker access
can mount any named volume, so do not grant that host account to untrusted
operators. Losing the volume requires a new DEV trust generation and another
reviewed overlap rollout; it does not justify copying a key out of Kubernetes.

Build the issuer image from the pinned base in `media-pki-issuer/Dockerfile`,
record its immutable local image ID (`sha256:...`), then initialize the named
volume once:

```sh
docker build -f scripts/dev/media-pki-issuer/Dockerfile -t voice-dev-media-pki-issuer:review scripts/dev/media-pki-issuer
docker image inspect --format '{{.Id}}' voice-dev-media-pki-issuer:review
python3 scripts/dev/media_pki.py prepare --issuer-image sha256:<image-id>
```

The CA is constrained to the exact DEV DNS identities `voice-voice`,
`voice-gameintegration`, and `voice-matchmaking.voice-dev.svc`, has `pathLen=0`,
and can sign only serverAuth leaves. The three leaf keys are distinct, each has
its exact DNS SAN and 90-day validity. Before exporting a leaf, the issuer
verifies its TLS chain and hostname. It also signs synthetic negative-chain
fixtures only in ephemeral storage and requires OpenSSL to reject `voice-space`,
`voice-gateway`, and `voice-matchmaking.voice-staging.svc` under the CA's actual
name constraints.
Before the one-time cluster cutover, `renew` creates fresh leaves under the
current DEV CA without changing its root. It uses the operator lock and refuses
to run once an apply journal exists, so it cannot invalidate a resumable receipt.
This recovery tool does not implement a later 90-day Kubernetes leaf rotation;
that requires a separately reviewed rotation operation and must not be attempted
by manually editing or deleting the protected receipt.

The named volume is the issuer's durable working custody; do not remove it as a
rotation or repair step. This tool has no plaintext key export or automated
backup command. If the volume is lost, treat that as loss of the issuer and
perform a separately reviewed new DEV trust generation: initialize an empty
volume, append its public root while retaining the existing JWKS bundle, then
issue new leaves and cut over. Never remove an old root while a deployed leaf
depends on it. An approved encrypted offline backup process is an operational
prerequisite before relying on this issuer for long-lived recovery; do not
improvise a host-side volume copy.

`apply --confirm-dev-pki-change` is the reviewed cluster cutover. It only targets
`voice-dev`, and requires the namespace's `voice.environment=dev` and
`app.kubernetes.io/managed-by=voice-dev` ownership labels: append the new public
root to `voice-media-ca.jwks-ca.crt` while preserving every prior bundle byte,
switch `voice-role` outbound JWKS trust to that key, create the public-only
`voice-matchmaking-principal-jwks-ca` and its server leaf Secret
`voice-matchmaking-principal-jwks-tls` only if absent, create GIS TLS only if
absent, replace the `voice-voice` TLS leaf with UID/resourceVersion CAS, and
restart Role/Voice to load the projected trust and certificate files. Chat and
Voice consume the dedicated Matchmaking CA Secret as read-only JWKS trust; the
Matchmaking pod consumes its TLS Secret read-only. The Matchmaking runtime URL
is `https://voice-matchmaking.voice-dev.svc:8443/internal/v1/principal/jwks.json`.
The Compose alias and all Staging identities use their separate environment
profiles and never use this DEV leaf.

The operator reads the documented public-only `voice-media-ca` Secret and
metadata, data-key names, type, ownership labels, and public `ca.crt`/`tls.crt`
fields for its own operation-created Secrets. It never GETs the `tls.key` value.
The inbound `ROLE_PRINCIPAL_CLIENT_CA_FILE` and `voice-media-ca.ca.crt` are
unchanged. DNS name constraints keep the outbound root from authorizing Space,
Gateway, or the Staging Matchmaking hostname.

The tool records CAS pins before changing resources and never overwrites an
existing operation journal. A forward-only boundary is persisted before the
first trust mutation, because a later leaf may depend on that trust. After that
boundary, `rollback` and `apply` re-entry refuse; the prior exposed Voice leaf
key is never restored. Continue the exact operation with its pinned issuer image
and protected journal:

```sh
python3 scripts/dev/media_pki.py resume --issuer-image sha256:<same-image-id> --confirm-dev-pki-change
```

`resume` verifies the fixed DEV namespace, CA bundle, Role trust configuration,
public leaf fingerprints, operation annotations, and UID/resourceVersion pins
before continuing forward. It fails closed on ambiguous drift; it does not
replace or reset the receipt. Before the forward-only boundary, use
`rollback --confirm-dev-pki-change` only when its saved resource pins still
match. Verify the Role and Voice rollouts, then use the separate GIS installer's
preflight/paused-start flow. Staging requires its own review and is never
addressed by this tool.

## DEV Music NATS maintenance

`nats_music_operator.py --profile voice-dev-current-deployment plan` and
`--profile voice-dev-current-deployment apply --plan-sha256 <digest>` are root-only
one-shot Messaging-actor maintenance. The explicit current-DEV profile binds the

identity. It requires the legacy generation marker to remain absent; if that

Service/controller/Pod/Secret/ConfigMap state is rechecked before writes. The mode only verifies the mounted
Messaging identity and can add its two canonical Music INFO/ACK grants after a
fresh signed-claim and authenticated client-listener preflight. It never creates
consumers.

Consumer creation is a separate explicit operation:
`nats_music_operator.py --profile voice-dev-current-deployment --mode bootstrap plan`, followed by
`nats_music_operator.py --profile voice-dev-current-deployment --mode bootstrap apply --plan-sha256 <digest>`. It only
replays the captured analytics-chat Job template when the live bootstrap
identity can authenticate, the root-prepared ConfigMap matches the captured
base ConfigMap, and INFO proves the Music durable is absent. The operator derives
the target ConfigMap only from the checked-out canonical bootstrap source. It
creates an immutable, baseline/source-bound ConfigMap enrollment for the new
replay Job and leaves the shared static ConfigMap and existing Job untouched.
The root-only journal binds that copy to the base ConfigMap UID/resource version
and data hash, namespace UID, stable baseline binding ID, and canonical target hash. Existing
enrollments must match the journal exactly; conflicts and drift stop the
operation. Before creating or reusing the enrollment, the operator revalidates
the entire plan-bound profile; afterward it allows only the exact ConfigMap
enrollment change and checks that all controller, Pod, Secret, and source state
remained unchanged. The replay uses a new deterministic Job name. Existing consumers are
a no-op; unknown INFO results, drift, an active Job, a missing Job/Secret, or
source mismatch stop the operation. The bootstrap credential is separately verified and, only
when its exact source ACL additions alone are missing, renewed through the
existing identity-preserving private issuer pipe. The canonical
`voice-nats-bootstrap-credentials` Secret remains unchanged. Per
[`deploy/nats/README.md`, “Existing account additive rollout prerequisite`](../../deploy/nats/README.md#existing-account-additive-rollout-prerequisite),
an immutable bootstrap credential is renewed by enrolling a new immutable
bootstrap-only Secret. This operator names that Secret with the stable DEV
baseline binding ID, binds it to the namespace UID and canonical Secret UID/resource
version, verifies the signed actor identity, and records the enrollment in a
root-only durable journal. The captured source Job and application mounts are
never edited; only the new replay Job points at the enrolled Secret. A
conflicting enrollment or missing/mismatched journal fails closed and needs
operator recovery; the credential digest exists only in the root-only journal.

The helper uses a loopback-only port-forward to the captured `voice-nats` pod's
4222 client listener; port 7422 is the NATS leaf protocol and is never used by
the client probe. Its role flag selects one of two fixed reply prefixes: the
existing Messaging inbox for the application actor or the bootstrap reply
prefix for the separate provisioning actor. The probe sends only the fixed
JetStream Consumer INFO request.
It does not create, publish, acknowledge, or subscribe to messages. Before
installing the root-owned helper, issuer, kubeconfig, and private backup
directory, review the source and bind the install to the target namespace UID,
DEV baseline binding ID, and captured Secret resource versions. Do not copy private
inputs to `/home/pmd` or print credentials or raw broker replies.
Install the reviewed source tree read-only under
`/home/voice-dev/operator/source` and invoke
`/home/voice-dev/operator/source/scripts/dev/nats_music_operator.py`; this keeps
the ACL, issuer, and preservation modules bound to the same source tree while
the executable, kubeconfig, backups, and private journals remain in the
root-owned `/home/voice-dev/operator` directory.

## DEV CompleteMatch transport identities

`complete_match_pki.py` and `complete-match-pki-issuer/` are a separate,
create-only DEV issuer for the Matchmaking → Gateway CompleteMatch transport.
This is a distinct operation and volume from the completed MatchSquad operator.
It creates only the Matchmaking server TLS Secret, the dedicated Gateway client
CA ConfigMap, and the Gateway client TLS Secret. The Matchmaking server leaf is
signed by the retained MatchSquad CA and is restricted to
`voice-matchmaking.voice-dev.svc` / `serverAuth`. Gateway receives a new,
separate client CA and a `voice-gateway.voice-dev.svc` / `clientAuth` leaf.
The MatchSquad CA is mounted read-only and its signer is never copied to the
new volume. Matchmaking principal-signing/JWKS keys are unrelated and must not
be used as TLS material.

The helper requires the exact source commit, immutable issuer image ID,
consumer-overlay digest and DEV namespace UID. It is Linux-only. `preflight` is
read-only; `prepare` requires `--confirm-dev-complete-match-pki-change` and
stores one same-operation stage in the dedicated private volume;
`apply`/`resume` use that stage to create only the three absent targets.
Every Kubernetes call selects `/home/pmd/.kube/config` and context `default`
explicitly with `kubectl --kubeconfig ... --context default`. Before invocation,
the helper checks the config and its
parent using metadata only: current-user ownership, regular non-symlink file,
single link, bounded size, no group/world permissions, and a non-group/world-
writable directory. The subprocess environment stays sanitized; ambient
`KUBECONFIG` is ignored, and the helper never repairs file permissions.
Creation has a durable intent, server-side dry-run, create-only API call and an
exact GET comparison before success is recorded. A retry can adopt only the
same staged content; drift or an uncertain result stops and preserves the
journal, volume and material. There is no overwrite, deletion, rollback or
new-operation recovery path. Capture the command's public receipt; never run
the issuer's raw `export` output into a terminal or log. The receipt includes
