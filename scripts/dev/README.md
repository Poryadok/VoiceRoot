## Updating WIP

### Auth/User database credential isolation for fresh installations

Fresh `credentials.py` issuance uses distinct `auth_runtime` and `user_runtime`
logins and independent passwords. The DEV renderer gives Auth only
`AUTH_DB_USERNAME`/`AUTH_DB_PASSWORD` Secret keys and disables in-process Flyway;
User receives its `USER_DATABASE_URL`. Auth stays Java/Spring. Neither login
owns a database, schema or table. Existing `voice` admin credentials remain the
bootstrap/migration authority; User migration Jobs use that authority separately
from the application's DSN.

After migrations and before app activation, bootstrap runs the fixed
`docker/postgres/provision-auth-user-runtime-roles.sql` through a DEV-only Job.
It grants each role CONNECT to its own database, public-schema usage, application
table CRUD and sequence usage/select, including default grants for future
admin-owned tables. Migration ledgers remain unavailable to runtime mutation.
User retains TEMP on its own database for identity-association transaction
preparation/batch tables, and SELECT on its schema ledger for startup validation.
Auth's identity DDL barrier retains its canonical owner plus PUBLIC SELECT ACL;
the provisioner removes direct runtime grants from that installation primitive.
PUBLIC CONNECT/TEMP and schema CREATE are removed only on auth_db/user_db;
the admin owner and other services' shared credentials remain unchanged.
Unexpected privileged/member/owning pre-existing runtime roles fail closed.
Provisioning diagnostics stay private in the Job; do not export those files or
database role statements. The source change does not retrofit a running stand.

For an existing stand, retain the actual migration/schema owner, inventory all
shared-role and migration/backup consumers, then prepare a separately reviewed
data-preserving credential adoption plan under its environment resource claim.
Stage dedicated roles and credentials, bind only Auth/User after qualification,
verify their own-database access and opposite-database denial, and run exact-image
registration/verification/login before revoking identified superseded access.
Do not rotate `POSTGRES_PASSWORD` globally, transfer object ownership, reset
data or run fresh bootstrap to adopt this change. STAGING/prod require separate
authorization and source/config evidence. Current DEV backend provenance is not
established by a frontend build's SHA.

The disposable PostgreSQL regression is `scripts/dev/auth_user_db_integration.sh`;
it requires a caller-owned empty PostgreSQL16 fixture with admin `voice`,
`PGHOST`, `PGPASSWORD`, independent `AUTH_DB_PASSWORD`/`USER_DB_PASSWORD`, and
the repository mounted at `/repo`. It creates only auth_db/user_db in that
fixture and deliberately leaves a privileged-role negative at the end. Never
point it at an existing database server. Static coverage is
`python3 -m unittest discover -s scripts/dev -p auth_user_db_test.py`.

Build and push images first, or import them into this single node's k3s
containerd. For local imports also register the repository@sha256 digest alias
with k3s ctr --namespace k8s.io images tag <imported-tag> <repository@sha256:digest>
so CRI can resolve it without an unpublished registry pull. Use an exact registry manifest digest. Frontends must be rebuilt
with dev API and WS URLs; reusing a staging frontend image targets staging.
The first installation's three frontend images were built from
`e0d875ba612517cd7aac3b184a2deff41cb0fec3` and imported locally, not pushed to GHCR.
They remain dependent on this node's image cache until published.

On a host with this repository and the intended kubeconfig:

```sh
python3 scripts/dev/update_images.py --image user=ghcr.io/poryadok/voiceroot/user@sha256:<64hex>
python3 scripts/dev/update_images.py --image user=ghcr.io/poryadok/voiceroot/user@sha256:<64hex> --apply
```

Repeat `--image` for multiple services. First command previews with server
dry-run; second updates only main app images and waits for rollout. Only the
owned `voice-dev` namespace is admitted. UID/resourceVersion CAS guards against
concurrent edits; an atomic ConfigMap lock serializes this tool. A failed or
uncertain mutation retains `voice-dev-image-update-lock`. Inspect the Deployment,
rollout and lock UID before manually resolving it; do not blindly delete it.
The updater never resets stores, applies migrations or changes configuration.

### Existing Auth/User credential adoption

`auth_user_adoption.py` is the bounded existing-data route for the retained
`voice-dev` namespace UID `15950fc8-0392-4053-9156-e95e78b596f9`, Auth clean
Flyway1..26 and User clean migrate19. It is separate from fresh bootstrap,
reset and global credential rotation. It preserves `voice` migration/object
ownership, global `POSTGRES_PASSWORD`, existing JWT/TOTP/storage keys and all
noncandidate workload specs. Auth stays Java. Never use this route on staging,
production, a recreated namespace or a different schema baseline.

Run the reviewed immutable operator package on the DEV host with Python3,
OpenSSL and the existing kubeconfig. Every Kubernetes call fixes kubeconfig
`/home/pmd/.kube/config`, context `default`, namespace `voice-dev`; transport
errors never print raw Kubernetes/SQL/HTTP payloads. The common
`voice-dev-image-update-lock` is atomic CREATE and is retained on uncertainty.
There is no force-unlock, role ALTER/rekey, automatic database DOWN/restore or
automatic rollback. The tool does not create deployment/PASS/acceptance records
or release the tracker resource.

The input manifest contains `operation` (unique lowercase name, maximum31
characters), full `source_sha`, exact `operator_sha256`, two immutable
`products` refs (`auth`,`user`), producer-qualified `runtime_ids` arrays, three
immutable `tools` refs (`postgres`,`flyway`,`migrate`), `recovery_mode`, and
`evidence`. Obtain the operator digest with
`auth_user_adoption_runtime.operator_fingerprint(package_root)` in Linux.
Each evidence entry binds a local JSON file by `path` and SHA256 `sha256`.
Required record kinds are `image_provenance`, `runtime_roles`, `recovery` and
`operator_review`. Each names its kind, `status: PASS`, exact product source,
operator digest, products and an actual retained evidence reference. Image
proof additionally binds exact runtime IDs, actual `node_accessibility: true`
and scope `published_oci` or `qualified_node_import`; a local build ID alone
is insufficient. Recovery and operator records name the actual independent
Dimas-8 review; recovery binds the selected mode. `qualified_image_restore`
requires original-OCI qualification. A recovered executable recipe is not that
proof. `reviewed_forward_only` requires its own actual reviewed recovery record.
These records are provenance references, not self-attesting booleans or new
human permission gates: preserve the underlying executed proof/review and do
not manufacture a PASS wrapper for missing evidence.
The three tool refs must exactly match `QUALIFIED_TOOLS` in the reviewed
runtime module (PostgreSQL16, Flyway11.3.0, migrate4.18.1 command-conformance
receipt). The legacy shared admin password must be a URL-safe issuance value;
an unexpected encoding is refused before mutation, never fixed by rotation.

After the candidate and operator qualify, acquire/reconcile the actual DEV
resource for this task and the complete mixed image package. Only Auth/User
may differ; retain all other49-map entries and do not attribute their sources
to the two candidate images. The prepare command performs actual read-only
inventory and server dry-runs, validates defaulted Job specs, generates one
private credential pair, and stores immutable original intent. Its output is
sanitized; journal contents are private0700/0600 and must not be attached to TT.

```sh
python3 scripts/dev/auth_user_adoption.py prepare --manifest /private/candidate.json --journal /private/operation
# Record the fresh baseline-observation.json under the actual resource claim,
# advance the actual task/resource deploy gates, preserving the same window.
python3 scripts/dev/auth_user_adoption.py run --journal /private/operation
```

The first run creates only the owned updater lock and encrypted backup set,
then stops pending actual off-node restore qualification. Copy ciphertexts,
`backup-manifest.json` and the separately custodied `backup.key` through the
authorized private channel. No plaintext dumps are written by the exporter.
AES256-CBC/PBKDF2 encryption is authenticated by a separately checked HMAC; the
manifest binds the operation, resource/window, original catalog and source.
Run the verifier off-node against existing immutable OpenSSL tooling and
caller-owned Docker Linux PostgreSQL16, without ports or shared volumes:

```sh
python scripts/dev/auth_user_adoption_restore.py --backup-directory PRIVATE_COPY --operation OPERATION --tools-image sha256:TOOLS_IMAGE_ID --output PRIVATE_REPORT.json
python3 scripts/dev/auth_user_adoption.py import-backup --journal /private/operation --backup-report /private/restored-report.json
python3 scripts/dev/auth_user_adoption.py run --journal /private/operation
```

The verifier checks encrypted copy identity before decryption, restores both
archives and password-free owner-role metadata into an empty private cluster,
and compares actual schema/object ownership, default privileges and real
migration history. Each dump has its own consistent snapshot; this is not a
cross-service snapshot while apps write. A backup does not authorize restoring
over newer user writes. Private fixture reports are explicitly ineligible for
the actual DEV backup gate. The whole operation has a15-minute source deadline;
expiry prevents further writes and retains recovery state. Do not begin while
waiting for unrelated builds/publication or assume expiry releases a lock.

After backup qualification, the same run resumes from terminal owned receipts
using the exact original credentials. It creates immutable operation SQL and
runtime Secret objects, runs real admin-owned Flyway/migrate Jobs, strictly
creates absent runtime roles without password ALTER, applies canonical grants,
then serially updates Auth and User through full-spec UID/resourceVersion CAS.
Actual configured Space must remain the same Ready peer; the operator neither
clears its address nor restarts it. A client timeout is not server completion:
Jobs, migration state and attributable PostgreSQL activity must reconcile.
Unknown/failed/dirty effects are not retried or adopted. No runtime role owns
persistent data; User retains ownDB TEMP and ledger SELECT, and the Auth barrier
retains owner/PUBLIC SELECT with no direct runtime ACL.

Completion requires actual source-qualified runtime IDs, old Pod/ReplicaSet and
old admin-session drain, ownDB allow/oppositeDB42501 denial with correct
credentials, canonical ACL/history/ownership, and one owned public
signup/fixture OTP/verification/fresh login/privacy/JWT-to-User-row flow. Tokens
and OTPs are never logged; the fresh session is logged out. The bounded account
is retained with private ownership intent for documented deletion; the tool
does not raw-delete rows or reset shared throttles. An ambiguous public
registration is not blindly repeated.

```sh
python3 scripts/dev/auth_user_adoption.py observe --journal /private/operation
# Record only an actual completed rollout/check with current workflow/resource
# guards. Green private tests do not create a DEV PASS or final acceptance.
python3 scripts/dev/auth_user_adoption.py finish --journal /private/operation
```

`finish` freshly verifies the full state and drains before deleting only the
exact owned lock UID/resourceVersion. A lost delete response is reconciled by
actual absence; a later owner's lock is never removed. Then obtain another
fresh version observation and use the supported tracker resource release.
On partial/uncertain effects retain journal, lock and `recovery_required` and
reconcile terminal Jobs/sessions before any recovery decision. No shared role
revocation, global password rotation, data destruction or implicit provider
activation is part of this route.
Before any migration/role/rollout effect intent exists, `abort --journal ...`
may close an unchanged-data operation only after actual owned server activity
has stopped and original state/authority revalidate. It deletes only its exact
owned lock; unused immutable source/Secret artifacts and the private journal
remain attributable. An aborted journal can never start effects again. Once a
DB/rollout intent exists, abort refuses and retains recovery state.

Focused checks use Docker Linux:

docker run --rm --network none --mount type=bind,source=REPO,target=/repo,readonly -w /repo/scripts/dev python:3.12-alpine python -m unittest auth_user_adoption_test auth_user_adoption_runtime_test auth_user_adoption_backup_test auth_user_adoption_smoke_test

The second command orchestrates only labeled disposable Linux containers. Its

collision/no-rotation, data/ACL/default grants, real server versus client
timeouts, authenticated archive restore and corruption rejection. It does not
qualify actual DEV backup custody, old-image rollback or configured topology.

### Exact candidate publication (workflow)

`DEV candidate image publication` is a standalone publish-only Actions workflow.
After normal review/integration, dispatch its default-branch publisher with the
selected product commit:

```sh
gh workflow run dev-candidate-publish.yml --ref master \
  -f product_sha=4e88e14e64300667e3349b08e75c4c31bf50b61e
```

This bounded consumer accepts only that product commit. It builds the eight
required DEV variants in one serial lane: Web, Admin, Developer Portal, Auth,
User, Notification, Realtime and the native Space installer. The source checkout
and publisher checkout are separate, clean and byte-verified. Explicit source
build arguments bind the four capability owners and native installer; frontend
build arguments target the DEV API and LiveKit endpoints.

Tags include the product SHA, actual run ID and attempt; existing or unavailable
tag state fails closed. No shared `latest`, master or full-SHA tag is overwritten.
The job independently resolves registry manifest bytes, selects exactly one
linux/amd64 platform manifest, pulls that immutable output, checks its image
config identity, and verifies actual JAR/binary/native SQL/frontend bytes.
Only the publishing job receives `packages: write`; PR validation is read-only.
No cluster credentials, SSH, deployment call or package visibility change exists.

The `dev-candidate-images-<run>-<attempt>` artifact records product and publisher
SHAs, authenticated run/attempt/job IDs, exact build arguments, source hashes,
index/platform/config digests and output checks. It also retains the selected
Auth image's public CA inputs. It contains no registry token or private keys.
New digests require a new canonical package and affected source/reference/crypto
qualification, preserving prior packages. Publication does not qualify node pull,
migrations, runtime flows, CI/release gates, shared-writer exclusion or deployment.
Before rollout, prove ordinary node pull for the complete app/init/migration/tool
image closure, including `migrations.GAMEINTEGRATION_IMAGES`, under actual DEV
custody. Keep the existing provider, storage, TLS and operation controls.

The separate `repair_clickhouse_memory.py` is a fixed DEV-only maintenance

then `--apply` from reviewed Linux source under the current TT DEV claim and

the 256Mi request, image, full remaining spec and PVC identity stay unchanged.

the digest-pinned single-container StatefulSet, quota, server dry-run, full-spec
and UID/resourceVersion CAS, Bound PVC UID before/after, then rollout/readback.
It uses the same `voice-dev-image-update-lock` as the app image updater and

table deletion, broad apply, pool tuning or Preservation service operation is
provided. Keep the TT resource window through independent verification;
neither the lock nor TT fences unrelated external kubectl operations.
The 4Gi rollout can still OOM while the ClickHouse server uses the image's
default `max_server_memory_usage_to_ram_ratio=0.9`. The separate
`mitigate_clickhouse_memory.py` is an opt-in DEV-only trial for that exact

operation marker plus the StatefulSet, current 4Gi Pod, and Bound PVC UIDs.

UID/resourceVersion/full-spec-guarded StatefulSet patch. `--apply` creates only

existing `docker_related_config.xml`. The image digest, 4Gi container cap,
256Mi request, PVC and other workload fields stay fixed. The script retains
the original lock on any uncertain result and releases it only after a new
Ready Pod, unchanged PVC/image/spec, parsed ratio `0.8`, and a startup log
reporting the derived 3.20GiB server cap. The ratio is a reversible trial,
not proof that startup OOM will stop. Keep the TT DEV claim/window until
independent smoke and resource readback; do not rerun the initial repair,
force-delete a pod, or remove a retained lock on timeout.
If independent stability verification finds that the same 0.8-policy pod is
again OOMKilled, `expose_clickhouse_errors.py` is a separate DEV-only diagnostic
step. It keeps ratio `0.8`, the 4Gi cap and all data/storage fields fixed, and

ConfigMap. The exact ClickHouse 24.8 image parses both settings and emits

Its preview verifies the failed Pod, StatefulSet revision, ConfigMap, PVC/PV
identities and quota, and server-dry-runs both the ConfigMap CAS patch and a
graceful delete of that one Pod with UID/resourceVersion preconditions. After
fresh TT DEV deploy admission, `--apply` acquires the shared updater lock,
rechecks the target, patches the ConfigMap and submits only that exact Pod
delete. It always retains the lock for operator readback, including after a
successful submission; inspect the controller-created Pod and `kubectl logs`
before any separately reviewed repair or lock disposition. This diagnostic
step is not a ClickHouse availability fix and does not imply product PASS.
When the Pod UID changes and its deleting actor cannot be established,

## Read-only DEV operation observation

operation_journal.py is an ordinary Linux operator reader. From a reviewed
checkout on pmdebook, as pmd, run:

```sh
python3 scripts/dev/operation_journal.py
```

The interface has no mutation, recovery, unlock, namespace, request-nonce or
arbitrary-file options. It makes only fixed GET requests through
/home/pmd/.kube/config, context default, for voice-dev, the exact
voice-dev-image-update-lock ConfigMap, Deployments and StatefulSets. Namespace
ownership labels must match DEV. The retained lock operation ID is not a request
nonce. The reader does not use the installed STAGING NATS bridge.

Output schema voice-dev-operation-observation-v1 includes namespace UID and
revision; lock UID, revision, creation time and operation marker; per-kind list
revisions; workload UID, revision, generation, readiness counts and immutable
container image references. Mutable image references become null. Source commit,
request ID and candidate remain null because these cannot be reconstructed from
image digests or lock age. There are no Secret GETs; env, specs, annotations,
credentials, tokens, private keys, DSNs, signed URLs, customer data and raw
exceptions are never emitted.

The two existing caller-owned Anton-12 recovery directories under
/home/pmd/voice-restore-anton12 have fixed metadata-only profiles for their
known receipt filenames. The reader uses directory descriptors with no symlink
following; parents must not be group/world writable, and operation directories
and regular single-link receipts must be private and owned by the caller. It
never opens receipt payloads: started.json contains original env/spec material.
Marker presence, file size and filesystem modification time are observations,
not authenticated journal events, operation success, proof of an inactive
executor or authorization to replay. Missing/inaccessible/insecure directories
are UNKNOWN; this does not mean no operation exists.

The reader collects twice. Changed observed revisions, projected state or receipt
metadata produce UNAVAILABLE and suppress the mixed evidence. Stable observation
is only a bounded observational interval, not an atomic cluster snapshot, a queue
census or future freshness guarantee. Root-private queue/inbox/processing, global
lock, journal version and queue/journal consistency remain explicitly UNKNOWN.
Both PARTIAL (exit 3) and UNAVAILABLE (exit 2) deny recovery admission. Every output
has mutation_authority=false and recovery_admission=false. Never pipe this report
to an unlock, deployment or resource-safety decision.

A full protected DEV journal requires a separately reviewed source binding and a
legitimate administrator installation of a DEV-only sanitized publisher. Preserve
root-only private state and writer controls; do not grant generic sudo, expose raw
journals, assume an empty queue, or retarget the STAGING bridge. The current reader
provides useful bounded evidence while that installation is unavailable. Record
the reviewed source SHA, actual ordinary-user read time and exact namespace/lock
pins with each receipt; reconcile unknown state with the current recovery owner.
This observation task must not gate independent baseline DEV recovery.
