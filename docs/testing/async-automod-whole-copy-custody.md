1. EXACT CRITERIA AND CLAIM TYPES
The required final state at the unchanged canonical account deadline D is removal of account-purpose raw links, payload-derived hashes/digests, pending retries and personal details; only already permitted opaque terminal fences/minimal nonpersonal existing-case snapshots remain. LIVE or validly restored accounts preserve EXACT still-eligible samples, consumed-through state, strike/mute count, source epoch/cursor, sanctions/appeals and restriction revisions. Space-origin erasure still removes its FROZEN bridge while eligible account-purpose state remains PERSONAL until its own applicable erasure. c2/c9/c13/c17/c19/c20 are not reopened.

Distinguish three claims in evidence:
E1 LOGICAL_OWNER_CLEANUP: current owner database transaction has removed the required live rows/joins and committed its local receipt. This is valuable and testable; it does not attest every replica/snapshot/WAL/cache.
E2 WHOLE_COPY_PHYSICAL_BY_D: every in-scope readable/recoverable personal copy, including its enabling keys, has actually reached the allowed final state by D. This is c27's stronger requested claim. No observed E1 receipt, ready=false, Secret rotation or restore scrub implies E2.
E3 CONTAINED_THEN_SCRUBBED: an offline/declared-restore copy is fenced and scrubbed against current positive terminal authority before access/replay. Existing canon permits this recovery barrier; it is not on-time E2 and cannot be relabelled as such.

These names classify evidence, not new product permissions. A particular available-storage execution may meet E1 and, if a complete actually controlled inventory is erased in time, E2 for that execution. A passing available execution cannot establish E2 for an unexecuting or unreachable copy holder. No new forensic-media requirement is inferred beyond c27: an ordinary readable old SQL snapshot, restorable dump or cached key is already sufficient to refute E2, without speculation about magnetic remanence.

3. ONE COMPLETE SOFTWARE-ONLY CANDIDATE EVALUATED, NOT SELECTED
Candidate C: owner-controlled sealed per-account state with no clear durable anti-abuse data outside its custody. This is a hypothetical replacement BEFORE activation, not an in-place v2 mutation or a new assigned wire version.

C would require one random, non-derivable per-lifetime content key and stable random relink authority owned by Auth, with all external persisted personal state sealed under that custody. The sealed domain must contain the complete producer event/expiry identity and hashes, pattern aliases/history, cursor/strikes/mute/sanction/appeal/report personal fields, mapping and retry metadata. The outside envelope may contain only independently justified nonpersonal routing/terminal material; account/event/sanction correlation must not survive as a hidden plaintext index. Global Messaging HMAC-derived aliases cannot remain outside this sealed domain. All decryption/relink authorization binds current owner incarnation, exact current lifecycle and purpose; terminal permanently disables relink and records the existing opaque fence. The LIVE restore path must reopen the SAME exact state, never seed a new namespace or reset a cursor/revision.

To avoid exported keys, C would execute plaintext detector/state work inside the owner's custody and return only allowed results; otherwise every Messaging/Mod process receiving a key/plaintext becomes another destroyable copy holder. That means a real ownership/transaction/transport redesign, not adding a key-fetch RPC to the current services. Atomic message persistence/evidence, local Mod state/sanction transaction and report participant contracts would all require an explicit compatible replacement. Auth remains Java; no implicit port of Auth or shared-database takeover is authorized. No concrete version number or migration is reserved by this rejected evaluation.

C would put ONLY ciphertext in PostgreSQL WAL, dumps and restic, and must exclude every content key, relink map and plaintext cache from those snapshots unless the same independent destruction mechanism covers them. It must also cover process heap, temporary files, spill/core dumps, old replicas, transport retry buffers and operations exports. Merely wrapping a per-account key with a retained global key while its wrapped copy survives is not destruction. Current PKI signing/TLS keys authenticate transport; they do not enforce these data-key rules.

Even granting all that replacement work, C fails the unchanged requested contract:
C-F1 FINAL STATE: sealed detector payloads/hashes remain retained data; c17/c19 permit no general encrypted detector archive or new anonymous-final-state exception. Destroying keys is not physical removal of those ciphertext bytes under the selected criterion. This alone prevents declaring C accepted.
C-F2 COPIED KEY/PLAINTEXT: if keys/plaintext are ever exportable, one paused consumer holding them through D does not execute zeroization. API/lease expiry, Secret deletion and a terminal ledger elsewhere do not destroy its copy. Removing all exports reduces the set of copy holders; it does not remove the owner process/host from that set.
C-F3 OWNER PAUSE: if only the owner retains the sole key, pausing the owner/key storage through D prevents software destruction there. A wall clock value stored beside the key changes no bytes without an executing trusted mechanism. An independently operating erasure device is a new capability/failure assumption, not supplied by Docker or a private listener. A hardware device alone would still not erase plaintext exported before the pause or satisfy C-F1.
C-F4 LIVE RECOVERY: keeping the sole key only in ordinary volatile memory makes an unrelated restart/power loss lose eligible LIVE state. Persisting/backing up that key to preserve exact LIVE recovery reintroduces copies whose deletion must be proven. Destroying every account key whenever custody is uncertain would violate live continuity. Splitting/sharing keys among ordinary services simply moves the same custody obligations to their shares and reconstructed-key caches.
C-F5 OWNER TIME: current lookup/census is not a future-deletion lower-bound promise. A typed C+P30D lease can bound future association retention only with every owner delete writer serialized to an enforced time floor; it does not solve finalstate/key/copy execution. A known DELETE with an unseen winning restore must preserve the same LIVE sealed state, so blind expiry cannot become terminal purge.

Moving all plaintext tables into the same Postgres/owner transaction instead of sealing them would remove one inter-service information delay, but still leave readable MVCC/backup/paused-owner copies and ordinary message-origin/report transport boundaries. It is not an alternative passing candidate and is not selected. Adding an outbox, sidecar, independent private listener or repeated sweep changes ordinary availability but does not cover a failure that pauses their shared host or disconnects the final copy repository.

5. OWNER-TIME BOUNDARY, WITHOUT A NEW DEADLINE
V30 at5100 is an actual transactional producer: lifecycle owner mutation and compact projection/two recipient intents commit together; nonterminal delivery does not acknowledge physical cleanup. terminalSnapshot now settles current account rows then seals only the durable ledger. Those are real advances over the old c19 source and are not reopened as missing implementations.

For a future horizon-capable representation, a concrete new internal owner operation would have to atomically lock/recheck the account lifetime, record a monotonic observation floor C using fresh owner DB time, and return an authenticated exact-generation promise that every subsequent NEW deletion timestamp t in that lifetime satisfies t>=C. EVERY delete path must enforce the floor. At5100 JdbcAccountRepository.deactivateExpiredGuests still assigns now(), while markDeleted/markDeletedAndIncrementSessionEpoch accept a supplied Instant; normal resolve is a plain lookup. Therefore no existing API carries that promise.

Such a future operation must reject rather than silently retime an imported/backdated or already-existing earlier deletion cycle. Existing DELETED deadlines remain immutable; restore is decided by the owner current-row guard at exact equality. A restored old database needs current floor/cycle/terminal lineage before issuing new promises. Backward wall-clock movement cannot revoke an already made floor; a trusted operational clock bound/floor policy is required, with explicit unavailability on a violated assumption. No duration, restore cutoff or timestamp is changed here. The inequality E=C+P30D<=D is only a derived bound once those conditions hold, not a deletion decision, physical erasure operation or new permission to retain orphan personal state.

172 must not add this speculative horizon endpoint merely to close c27: even a perfectly implemented floor leaves C-F1 through C-F4 unresolved. Current lifecycle/positive-terminal APIs and native deadline guard remain the selected implementation.

6. MINIMAL INDISPENSABLE BOUNDARY — FINITE, NOT A QUESTION LOOP
There are three independent prerequisites for a replacement to be reconsidered:
B1 EXECUTION/DECISION DOMAIN: an explicit supported failure model must leave an executing authoritative mechanism able to settle the actual winning delete/restore and perform erasure at every in-scope copy before D. All-copy host/storage pause through D violates this prerequisite even if the account deadline is perfectly known. A software retry implementation cannot supply it. No bounded network/worker delay or zero-duration last-moment restore propagation may be invented. Co-custody could remove a remote decision hop but still needs an executing owner and complete copy control.
B2 COPY/STORAGE CUSTODY: either prevent all personal copies outside that erasure domain in the new representation, or provide actual independent selective destruction for them, including restic/dumps/WAL/old processes and recovery keys. The existing nightly restic policy is not that facility. A backup recipe/hash/signature proves copy integrity, not selective timely destruction; preserving LIVE current-tail recovery remains mandatory. No broad backup deletion, key destruction or infrastructure provisioning is authorized by this review.
B3 ALLOWED FINAL STATE: keeping any encrypted/pseudonymous detector residual after D requires a genuinely changed accepted finalstate plus a whole-key-copy destruction proof. That is not allowed under this request, so this branch is CLOSED here. Under unchanged finalstate, actual removal remains required. Classifying a residual anonymous or calling cryptographic inaccessibility physical erasure is not an implementation choice that may be slipped into a new version.

Holding all three unchanged together with the named arbitrary-total-partition/paused-copy faults leaves NO candidate. This is a finite no-candidate boundary, not an assertion that no erasure architecture can ever exist. No numeric change would cure B1/B2. A future continuation is justified only by concrete new custody/execution capability evidence satisfying B1/B2 under the same finalstate, or an explicitly changed requirement/failure/finalstate mandate. Repeating the current-v2 inventory, adding another private retry channel, or asking162 to rediscover the same gap is not a resume condition.

For AVAILABLE-STORAGE execution,156 can demonstrate: actual winning owner authority settles; exact current facts reach participants; local transactions perform E1 independently of evidence ACKs; all participating live copies covered by that particular proof are erased; ordinary LIVE restore preserves exact state. If the named failure destroys these prerequisites, record the actual missed/unproven physical deadline and late cleanup, never a grace or E2 PASS. Canon already permits E3 on supported offline restore; do not make every normal process restart depend on a new external key/sink service.
