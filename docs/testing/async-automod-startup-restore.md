1. DECISION
Start local key publishers and protected listeners independently of peer domain readiness. Gate methods and workers by local domain barriers. Auth first establishes trustworthy terminal/lifecycle authority; Moderation then imports a complete terminal snapshot and purges restored private state; Auth and Moderation subsequently reconcile restrictions using their protected surfaces. Only then open the relevant public/admission surfaces. No service waits for the other service's public readiness to provide the private capability needed to establish that readiness.

A live local DB can serve as its own authoritative current store on ordinary restart after migrations and local integrity checks. A restored DB is not proven current merely by passing those checks or returning complete=true. Restore requires a verified recovery cut, including terminal history that survives the rolled-back backup. If that history is unavailable, recovery is fail-closed; this is an actual data-integrity prerequisite, not an unresolved product choice. Mutual agreement between two old backups cannot satisfy it.

3. NETWORK AND LISTENER CONTRACT
Define three distinct predicates: process-live (local loop/listeners work), authority-ready (the service's own trustworthy domain prerequisite is satisfied), public-ready (its required bootstrap reconciliation is complete). A liveness/startup probe must not depend on a peer's public-ready state. /ready returns unavailable until public-ready. /health semantics must be documented consistently across Compose and Kubernetes; do not make a dependency mistake by pointing one environment at a different predicate accidentally.

Kubernetes: add dedicated private ClusterIP Services voice-auth-authority and voice-moderation-authority with publishNotReadyAddresses=true, exposing ONLY protected principal/automod and mTLS JWKS ports. Keep ordinary public Services readiness-gated. No Ingress or public port for these bootstrap surfaces. Bootstrap client URLs resolve these private Services directly, not through Gateway/public Service. Cert SANs must include the selected internal service DNS names. NetworkPolicy must permit only the actual caller services and required ports, plus DNS; certificates and signed-purpose authorization remain mandatory even where policy permits connectivity. Any remaining public Service mapping of a private port must preserve the same handler authorization; clients must use the bootstrap route for this protocol.

publishNotReadyAddresses intentionally permits routing to not-public-ready Pods; therefore it is safe only with private ports and per-method gates, not as a replacement for them. A normal headless Service is not a workaround: Pod DNS records also depend on readiness unless publishNotReadyAddresses is enabled. Choose the dedicated ClusterIP route consistently rather than relying on accidental Pod IP reachability.

Compose: start Auth and Mod based on their LOCAL infrastructure prerequisites, without a reciprocal service_healthy dependency. Remove/avoid any transitive public-readiness back-edge introduced by the new wiring; validate the rendered dependency DAG. Private listeners bind internal container interfaces without host publication. Peer bootstrap uses retrying direct service DNS. Existing downstream Messaging public startup may wait for Auth/Mod domain health only if neither Auth nor Mod waits for Messaging's public health/JWKS at startup. Verifiers must lazily fetch peer JWKS when needed; a configuration entry for an inactive peer must not force an eager blocking remote fetch before local publisher startup. A dedicated internal issuer listener/sidecar is needed only if an otherwise unavoidable dependency prevents that peer process from starting; do not create that dependency in this implementation.

JWKS endpoint authentication is mTLS certificate identity; it must not require a service JWT whose verification first needs that same JWKS. It publishes public key material from the existing service issuer, not another signing authority. Service-principal bootstrap verification must not depend on user-session projection readiness. Invalid local cert/key/config is a startup error; temporary peer/network failure keeps domain gates closed with bounded per-attempt deadlines and backoff while liveness remains truthful. Never turn peer outage into an unconditional successful readiness response.

4. FINITE ACTIVATION ORDER AND METHOD GATES
P0 CLOSED LOCAL START. Create a new boot ID and bind it to local store identity/schema and deployment/recovery generation. Never reload a persisted true readiness flag. Apply local migrations/config/key checks, start private issuers/listeners and local probes. Public handlers, evidence application, sanction dispatch, account-affecting expiry and legacy/manual restriction writers remain closed. Purely destructive local privacy-deadline cleanup may run early if it cannot create/publish an effect or reactivate a subject.

P1 AUTH AUTHORITY. Verify that the local authoritative DB is the current live store or complete the declared restore procedure in section 6. Apply due privacy cleanup and establish the authoritative terminal ledger. Then enable Auth private ResolveModerationSubject, ListTerminalModerationSubjects and ReconcileModerationRestriction; they do NOT wait for Mod/public readiness. Resolve reads Auth's own binding/lifecycle/terminal state without refreshing Mod projection recursively. Its returned auth_restricted is persisted authority state, not permission to issue a session during boot. Public session issuance/refresh and Messaging new-send admission remain gated separately. Do not persist a temporary bootstrap ban as a real sanction.

P2 MOD PRIVACY IMPORT. Fetch the complete authoritative terminal snapshot via the protected route. Validate authority/recovery generation, snapshot identity/manifest, completeness and canonical IDs; import a monotonic UNION of terminal fences and purge every affected participant, including pending evidence, sanctions/restriction intents and event publication payloads as required by c9. Never replace the local terminal set with a smaller remote set. Batching is allowed, but the boot privacy receipt commits only after every batch/participant succeeded; no partial snapshot can open a gate. A crash repeats idempotently. Snapshot metadata and import receipts contain no raw account mapping or content.

P3 PRIVATE RESTRICTION REPAIR. After P2, enable Mod GetEffectiveRestrictionSnapshot for authenticated Auth and enable the dedicated restriction reconciliation coordinator. Derive current effective desired state from current local sanctions under the existing account lock; discard/rewrite stale queued desired values under that same authority, respecting terminal/deadline precedence. Keep ordinary consumer/outbox/public work closed. Auth's private reconciliation from P1 is now reachable, so Mod can deliver exact intents. Mod's snapshot callback may call P1 Auth Resolve, but neither method may hold an account DB transaction/lock across the reciprocal RPC. Read identity/version -> network -> local compare-and-set/recheck lifecycle, with bounded retry on change. This avoids a lock-level cycle even when the listener-level cycle is fixed.

P4 FINITE LOCAL COMPLETION. Auth takes a bounded, stable bootstrap census/cut of its existing live subjects and obtains current Mod restriction snapshots for that census, reconciling exact per-account revision and desired state locally. Mod similarly closes its bounded startup set of outstanding desired restriction work with exact acknowledgements. New accounts after the census cut use the same per-account admission procedure before sessions/sends; they do not extend the census forever. Concurrent new changes use the normal revision protocol and are not erased by boot completion. Each service records a receipt tied to THIS boot/store/recovery generation, the source terminal snapshot, census bounds/completion and zero unresolved required items.

P5 OPEN OWN DOMAIN. Auth may open public session/admission surfaces after P4 for Auth; Mod may open its evidence intake, send-restriction read surface, normal workers and public paths after P2-P4 for Mod. Neither waits for the other's public-ready boolean: private P1/P3 capabilities supply their prerequisites. Source provision/ingestion remains fresh-Auth-checked after opening. A local restored account with unresolved integrity divergence remains denied and cannot be counted as completed in the boot census; for initial activation use global not-ready until the required census is closed, rather than inventing an unimplemented partial-readiness exception.

Messaging also starts with its producer/outbox gates closed. Before opening new-send admission, it imports Auth terminal fences, purges its private evidence participants, validates the producer epoch/cursor against Mod's protected provisioning acknowledgement, and can read current protected restriction/lifecycle state. Its private key publisher must not require send readiness. Every enabled producer uses that same gate. A lost response to an already committed send still returns the previous committed result according to c9; it does not create a fresh record during bootstrap.

Steady-state boundaries: a boot census proves a finite bootstrap cut, not a cross-database atomic view forever. Auth public issuance/refresh must run the per-account protected restriction refresh before admitting a new session, then recheck local subject/lifecycle/revision in its own commit; failure denies admission. Messaging already performs fresh protected existing-state checks at admission. A restriction committed after such an admission check has the existing c9 in-flight semantics; do not claim zero network race or cross-DB linearizability. All ongoing effects retain per-account local locking, current terminal/deadline checks and revision/idempotency guards. A newly learned terminal fence closes/purges its account even after global boot has completed.

5. MINIMUM INTERFACE AND RECEIPT DELTAS
Keep existing signed caller/audience/method/body binding. Add a sealed terminal-snapshot response with authority_generation, snapshot_id, terminal high-water/cut identifier, total count and canonical payload digest, plus complete. A bounded whole response is acceptable; if paging is needed all pages belong to the same sealed cut and the final manifest proves the full count/hash. An over-limit response is unavailable, not truncated complete=true. A complete empty snapshot is valid only from an initialized authoritative current store; it never initializes a restored consumer as a fresh installation by inference.

The generation identifies a trusted deployment/recovery history, not a timestamp invented by the requester or a counter accepted merely because it is larger. Store and compare the receipt with the local boot ID. This metadata prevents mixing cuts/pages/boots; it does not independently prove that a rolled-back authority has all historical erasures. Section 6 supplies that prerequisite.

ReconcileModerationRestriction acknowledgement binds exact subject/account/request revision and desired state (or request digest), plus current terminal state. Deleted/terminal wins over both set and clear. On remote higher revision, re-read current local authoritative revision before classifying stale-flight versus restoration divergence; neither case acknowledges the old request. On unknown preexisting suspension, preserve c9's no-implicit-reactivation rule. Do not use an unversioned writer as fallback.

Provision response must bind source_epoch and acknowledged through-sequence. As accepted by 156, remoteThrough > localLastSeq or epoch conflict closes that account's producer admission with a typed restoration-divergence result; no baseline reset. HMAC retired-key IDs/tombstones survive ordinary restart; restore checks must run before fresh sends so old metadata cannot reset live pattern history. Key-retention policy remains c9/156's existing derived horizon, unchanged here.

Expose health only as aggregate gate/reason/counter data; do not expose account IDs, terminal subjects, snapshot payloads or key material there. Suggested closed reasons are LOCAL_START, AUTHORITY_RECOVERY, TERMINAL_IMPORT, RESTRICTION_RECONCILIATION and RESTORE_DIVERGENCE. These are technical diagnostics, not new product statuses.

6. RESTORE MATRIX AND RECOVERY OWNERSHIP
R0 ordinary process restart, authoritative databases current: re-establish local gates, fetch a fresh complete snapshot each boot, reconcile bounded current work, open. A previous Pod's ready receipt cannot authorize this Pod.
R1 Mod backup behind current Auth: P2 imports current terminal fences first. Re-derive desired sanctions from recovered authoritative Mod history. Auth projection revision greater than Mod's CURRENT local revision is a real missing-history signal: quarantine and recover Mod journal/PITR; Auth's bool alone cannot reconstruct sanction provenance, appeals or history. Do not fabricate a higher revision to overwrite Auth.
R2 Auth backup behind current Mod: Auth P1 remains closed until current terminal/lifecycle history is recovered. Then import current restriction projection from Mod through P3/P4. A current Mod terminal set can assist recovery only with independent proof that it contains the full authoritative cut; an arbitrary subset does not become Auth's authority.
R3 both backups behind: their mutual consistency provides no erasure or restriction freshness proof. Restore terminal/lifecycle truth and Mod sanction history from verified non-rolled-back recovery records/WAL/PITR through the approved recovery cut. Without those records remain closed; local JWKS/liveness may operate. No public-ready override, baseline reset or last-write-wins merge.
R4 Messaging behind Mod: fail new sends before any commit on epoch/cursor divergence; recover source state/acknowledged history. Do not permit an empty restored outbox or retired-key table to define a new baseline.
R5 restore while another replica/worker is live: first quiesce/drain affected producers and dispatchers and fence old replicas from the cutover generation. Only then restore stores and start the boot protocol. Do not perform a live DB replacement under an open process. A generation/store change invalidates receipts and worker leases; a worker rechecks its gate before processing, local commit and external dispatch. Quiescing is necessary because a local fence cannot recall an RPC already in flight.

Concrete recovery deliverable for 156: persist in DEPLOYMENT/ExecPlan a restore manifest containing store identities, backup/PITR boundaries, authority generation, terminal snapshot manifest and proof of the latest retained authoritative recovery cut. Provide the independently protected terminal/WAL recovery material and verify its completeness before changing the declared generation. A manifest without recoverable records is not proof. Capture the cut after affected writes are quiesced; when an unexpected outage prevents proving that the recovered cut includes every acknowledged erasure, do not assert privacy-safe restoration. Normal live startup does not require fabricating a restore manifest. Production backup/restore must preserve the c9 terminal history rather than treating an old application backup as sufficient.

This is not a new atomic distributed transaction. Auth local terminal commit, Mod local purge/import, projection reconciliation and generation-controlled traffic admission are separate ordered operations with durable receipts and fail-closed gaps. An unannounced storage rollback to an old but structurally valid database cannot be detected from that database alone. The supported recovery procedure must exclude that operation; it cannot be made safe by adding a ready column or comparing two rolled-back counters.

N6 Crash after any import/purge participant or batch: restart remains closed and completes idempotently; no pre-crash ready receipt is reused. Terminal-set union cannot drop a known fence.
N7 Erasure/deadline during bootstrap or immediately afterward: fresh subject/deadline checks dominate stale live bindings, buffered evidence and pending publication; no erased private payload is recreated. Tests respect the documented already-admitted in-flight boundary rather than asserting impossible cross-DB atomicity.
N8 Restored queued clear/ban conflicts with current local effective sanctions: re-derive under account lock before dispatch. ACK loss/retry has one logical result; older reply cannot remove newer intent. Remote revision above CURRENT local authority produces RESTORE_DIVERGENCE, not a fabricated new revision.
N9 Auth->Mod snapshot->Auth Resolve while other reconciliation executes: no DB transaction/lock held across reciprocal RPC; bounded retry on lifecycle/version change, no lock cycle or use of stale binding after CAS failure.
N10 Auth census under concurrent account creation/restriction changes: finite cut completes; post-cut account issuance uses per-account admission; no new account bypass and no endless bootstrap census. A completed cut is not asserted to be an eternal synchronized snapshot.
N11 Mod-only/Auth-only/both-store rollback: exercise R1/R2/R3 with an erased subject and newer restriction. Missing authoritative recovery material never opens public readiness even if both old DBs agree. Verified recovery removes the fence violation before opening.
N12 Msg restored cursor/key metadata behind Mod: new ordinary, Bot, ghostOnly, forward and game sends all deny before commit; no automatic epoch/baseline reset, no key retirement rollback immunity. Existing exact replay does not create evidence.
N13 A rolling new Pod cannot borrow another Pod's boot receipt; generation change closes gates and old workers cannot continue through cutover. Restore requires actual quiescence/drain evidence, not merely removing a public readiness endpoint.
N14 Existing expiry/manual/appeal/publication paths are started against a restored erased account: every account-affecting path obeys the barrier and terminal priority; pure privacy deletion may safely progress while authority is unavailable.
