RESULT
The proposed construction is a meaningful alternative to investigate, not ruled out by the paired-world argument for the CURRENT retained representation. Expiring only an identity association could preserve an anonymous state in both worlds, and Auth could relink it only for the still-live world. Therefore c19 is NOT a theorem that every redesigned architecture is impossible.

However, this route is NOT an implementable unlink operation on accepted account-core v2. The actual state has multiple raw identity copies, identity-bearing immutable hashes, cross-service joins and globally keyed content fingerprints. Its remainder is explicitly classified PERSONAL by c17. No source-backed claim of non-identifiability after deleting one bridge can be made. Retaining those bytes and calling them anonymous would quietly violate the existing final state. The immediate selected c19 producer/terminal-race work and precise current-architecture acceptance limitation stand.

1. WHAT THE PROPOSED OBSERVATION HORIZON WOULD PROVE
Let C be an Auth-owned, current serialized LIVE observation and suppose the owner guarantees that every later deletion in that account lifetime uses an authoritative deletion time t>=C. Then an identity association lease ending at E=C+P30D expires no later than the unknown future deletion deadline D=t+P30D. This is a bound from known positive owner authority, not a guessed deletion time. No new numeric threshold is required for that inequality.

At E an isolated recipient could remove an association without claiming the account terminal. A valid LIVE account could later recover EXACT retained state through its stable owner-only token; a terminal account could not. A known DELETE with an unseen valid restore can likewise expire only its association, then relink the same preserved live state later, rather than reset samples/strikes. This is conceptually different from c19's destructive Purge, which permanently fences the subject and cascades the state.

But today's ResolveModerationSubject does NOT promise that lease. AuthModerationStore.resolve is a plain current lookup, without an owner-serialized future deletion-time lower bound. JdbcAccountRepository.deactivateExpiredGuests writes deleted_at=now() (transaction-start time). markDeleted and markDeletedAndIncrementSessionEpoch accept a supplied Instant. V27 derives purge_at from that value. A deletion transaction can start before C, become visible afterward, and yield t<C; arbitrary privileged backdating also breaks the inequality. A new typed horizon would require fresh owner time under the account lock, all deletion writers enforcing that temporal promise, and explicit handling of restored/legacy/imported earlier deadlines. Client receive time, JWT exp, observed_at from a stale response or a timestamp invented by Mod is not a substitute. Do not modify canonical deadline timestamps merely to make the inequality true for existing deletion cycles.

3. WHAT A DIFFERENT CUSTODY ROUTE WOULD HAVE TO CHANGE
Any viable route must remove ALL the associations above by E, not just automod_subjects.account_id, while retaining exactly the still-eligible detector, cursor, effective sanction, appeal and restriction-revision state. The independent retained state must have no raw identifier, raw-ID-derived hash, retained event/sanction join, globally recomputable identity selector or content fingerprint that re-identifies it through retained system data. A token kept by the recipient must be an unlinked random internal address, not a bearer capability that recreates identity without fresh owner authority.

Auth's stable relink token/key would have to be random, purpose-separated, non-recomputable from raw account ID or a surviving global secret, retained only for the same nonterminal account lifetime, and irreversibly unavailable on real terminalization. Relink would require fresh protected Auth current LIVE binding, exact incarnation/generation, local old-state/cursor/revision matching and atomic reattachment. Old signed proofs, old cached tokens, old DELETE cycles and restored backups must not relink after terminal. A LIVE restore recovers the SAME state, never a new source epoch/pattern namespace or zero restriction. No arbitrary account can claim an orphan capsule.

For encrypted opaque capsules, all fields/hashes/join metadata that carry identity or known-content correlation must be inside the protected representation. Use of encryption would also require an actual per-account non-derivable key-custody/destruction model, expiry of every consumer-readable copy, cache/dump/replica/backup treatment, and an independently current terminal/restore boundary for Auth's token/key store. A retained global wrapping/derivation key plus an old raw-ID mapping, recoverable old token or old per-account key can defeat purported destruction. An expiring API permission is not destruction of a cached decryption key. An unavailable/paused machine does not physically scrub its memory/disk merely because a token's expires_at passed.

That could be a different cryptographic-erasure design in principle. It is not present in c9/c17 or the inspected v2 schema. It must not be described as physical erasure of retained ciphertext, or as already authorized key infrastructure. Current canon explicitly requires removal of payload-derived hashes/digests and permits only opaque terminal fences/minimal nonpersonal existing-case snapshots at account purge; no general encrypted detector archive exception is established. An actual accepted non-identifiability/erasure classification and custody proof, not merely a new stable token, would be needed before substituting this final state.

Implementing such a route would require a new versioned producer/consumer representation before activation, complete sanction/report/appeal ownership migration and recovery design. It cannot silently mutate active v2 cores or invalidate existing equality receipts. If unactivated v2 is replaced, pin a new protocol/hash/migration contract and fail closed on unsupported restored streams; do not reinterpret existing bytes. No new design or keys are implemented/provisioned by this investigation.

4. BOUNDED FEASIBILITY NEGATIVES
R1 Delete only Mod account association and attempt permitted joins from sanctions/action/event outbox and inbox JSON: current schema still exposes the identity. This alone disproves the proposed minimal patch, without needing a speculative attack.
R2 Delete both Mod/Messaging mapping rows but retain v2 core/expiry bytes and hashes: the account binding is still embedded or cryptographically committed; no anonymous-final-state receipt is valid. Deleting cascaded state instead fails LIVE continuity.
R3 Expire a bridge while valid pending v2 sequence and old strike exist: neither early expiry nor payload rehash nor first-event reprovision is accepted. Recovery must preserve exact sequence/hash/count/strike/sanction revision.
R4 Use current plain LIVE lookup at C while a deletion transaction started earlier or supplies earlier deleted_at, then commits later: C+P30D must not be advertised as a proved expiry bound. Test any future typed horizon against every owner deletion writer and legacy deadline.
R5 Known DELETE/unseen LIVE restore: any proposed relink design must preserve exact LIVE evidence through association expiry and later owner relink; direct Store.Purge irreversibly fails that requirement.
R6 After real terminalization, replay old token/proof, restore an old Auth token map, or use retained global derivation/wrapping keys: none may recover identity or key. Existing v2 does not supply that proof; protected API denial alone is insufficient if bytes/key copies remain.
R7 Proposed encrypted capsule, paused recipient, copied cache/core dump and old backup: an expired lease does not certify key destruction. No claim of physical erasure may be issued on clock comparison alone.
R8 Same live account reconnects through fresh owner token: full still-eligible state and restriction revision agree exactly, without relaxing c2/c9 windows. Another account, new lifetime or lost CURRENT recovery cut cannot attach that orphan state.
